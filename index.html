1. [홈쇼핑] 결제 승인 시 재고 차감 — 비관적 락에서 조건부 원자적 UPDATE로

홈쇼핑 이커머스 플랫폼 · home-shopping-backend

한 줄 요약: 비관적 락의 대기 시간이 트래픽 증가에 따라 병목을 유발하여, 락 없이 SQL 조건절로 정합성을 보장하는 조건부 원자적 UPDATE로 전환하고 k6 테스트 기준 p95 응답시간을 78.6% 단축했습니다.

문제

  • 동시 결제 시 "재고 확인 → 차감" 사이의 시간차로 인해 재고보다 많은 주문이 성공할 위험이 있었습니다.
  • 1차로 PESSIMISTIC_WRITE를 적용해 정합성은 확보했으나, 동일 상품 행에 요청이 집중될 때 트랜잭션이 락 대기 상태에 빠지는 병목이 발생했습니다.
  • k6 부하 테스트(동시 사용자 1,000명 구간) 결과, p95 응답시간이 6.93초까지 증가했습니다. 락을 잡은 채 비즈니스 로직을 수행하는 동안 DB 커넥션 점유가 지속된 것이 원인이었습니다.
  • 주문 생성 시점에 재고를 선차감함에 따라 결제 미완료 주문이 재고를 점유하는 구조적 문제도 존재했습니다.

해결

  1. 차감 시점 이동: 재고 차감 시점을 주문 생성 단계가 아닌 결제 확정(confirm) 단계로 변경하여 불필요한 재고 점유를 방지했습니다.
  2. 조건부 원자적 UPDATE: 비교와 차감을 단일 SQL문으로 결합하여 DB 행 단위 원자적 처리를 보장했습니다. 영향받은 행 수가 0인 경우 재고 부족 예외로 처리합니다.
  3. 품절 상태 전환(SOLD_OUT) 역시 동일 UPDATE 문 내 조건절로 통합 처리하여 상태 변경 간 격차를 제거했습니다.

2. [홈쇼핑] 선착순 쿠폰 발급 — Redis Lua 원자 판정 + Kafka 비동기 저장

홈쇼핑 이커머스 플랫폼 · home-shopping-backend

한 줄 요약: 중복 발급은 방지하나 전체 수량 초과를 제어하지 못하던 기존 구조를, 판정 로직 전체를 Redis Lua 스크립트로 원자화하고 DB 저장을 Kafka 기반 비동기 구조로 분리하여 해결했습니다.

문제

처음 구조는 "Redis로 거르고 DB 유니크 제약으로 최종 보장"이었습니다.

[요청] → Redis SADD coupon:{id}:members   (중복 확인)
      → Redis INCR coupon:{id}:count      (수량 카운트)
      → DB INSERT member_coupon           ★ (member_id, coupon_id) 유니크 제약
  • 유니크 제약의 한계: (member_id, coupon_id) 유니크 제약은 "한 사용자가 2장 받는 것"만 막습니다. "선착순 100명"처럼 전체 수량을 제한하는 문제는 제약으로 표현할 수 없습니다.
  • 비원자성: SADD와 INCR이 별도 명령이라 그 사이에 다른 요청이 끼어들 수 있었습니다.
  • 요청 경로의 DB 의존: 매 요청마다 쿠폰 조회와 INSERT가 동기적으로 일어나, 트래픽이 몰리면 DB 커넥션이 병목이 됩니다.

해결

구성역할
Redis선착순 판정의 기준. 쿠폰 메타(총수량·기간)도 Redis에 올려 DB 조회 제거
Lua 스크립트판정 과정 전체를 원자적으로 처리. 실행 중 다른 명령이 끼어들 수 없음
Kafka요청이 몰리는 순간의 DB 부하를 분리해 순서대로 처리
-- KEYS[1] = coupon:{id}:meta, KEYS[2] = coupon:{id}:members
local meta = redis.call('HMGET', KEYS[1], 'total', 'start', 'end')
if not meta[1] then return -3 end                                            -- 쿠폰 없음
local now = tonumber(ARGV[2])
if now < tonumber(meta[2]) or now > tonumber(meta[3]) then return -2 end   -- 기간 아님
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return -1 end       -- 중복
if redis.call('SCARD', KEYS[2]) >= tonumber(meta[1]) then return 0 end     -- 소진
redis.call('SADD', KEYS[2], ARGV[1])
return 1                                                                     -- 성공
  • 카운터 제거: 발급 수를 SCARD(Set 크기)로 계산해 별도 카운터와 Set이 어긋날 여지를 없앴습니다.
  • 키 해시태그: {id}를 써서 Redis Cluster에서도 두 키가 같은 슬롯에 놓이게 했습니다.
  • 메타 적재 시점: 쿠폰 생성 트랜잭션의 afterCommit에서만 Redis에 올려, 롤백된 쿠폰이 Redis에 남는 것을 막았습니다.
  • 발행 실패 보상: Kafka 발행이 실패하면 SREM으로 Redis 자리를 반납합니다.
  • Consumer 멱등성: Kafka는 최소 1회 전달이라 같은 메시지가 다시 올 수 있습니다. 유니크 제약 위반은 "이미 처리됨"으로 보고 무시합니다. 유니크 제약의 역할이 "수량 제어"에서 "멱등성 보장"으로 바뀐 셈입니다.
  • 장애 격리: DefaultErrorHandler로 1초 간격 3회 재시도 후 coupon-issue.DLT로 보냅니다.

트레이드오프

항목내용
최종 일관성응답(202) 시점과 DB 저장 시점 사이에 짧은 지연이 있어 "내 쿠폰함"에 즉시 보이지 않을 수 있음
Redis가 판정의 기준Redis 장애·유실 시 발급 상태를 DB에서 재구성하는 절차가 필요
인프라 복잡도Kafka 운영 부담이 추가됨. 대신 DB가 트래픽 피크에서 분리됨

결과

  • 판정이 단일 Lua 스크립트 안에서 끝나 총수량 초과 발급이 구조적으로 불가능해졌습니다.
  • 발급 API의 요청 경로에서 DB 접근이 0회가 되었습니다.
  • k6로 100장 쿠폰에 서로 다른 유저 1,000명이 동시에 요청한 결과, 초과·누락 없이 정확히 100장이 발급되었습니다(정합성 100%). 평균 응답 1.5s, p95 2.06s를 측정하고 병목 원인을 분석했습니다.

3. [위드도그] FK 제약 조건 위반 및 연관 엔티티 삭제 제어

위드도그 (WithDog) · with-dog

한 줄 요약: 게시물 삭제 시 연관된 자식 엔티티(알림·댓글·좋아요) 존재로 인한 Foreign Key 제약 위반 문제를, 의존성 그래프의 리프(Leaf) 노드부터 명시적으로 제거하는 서비스 레이어 로직으로 해결했습니다.

문제

  • 댓글·대댓글·좋아요가 달린 게시물을 삭제하면 DataIntegrityViolationException이 발생했습니다.
  • Comment, PostLike는 post_id를, 대댓글은 원본 댓글의 parent_id를, Notification은 comment_id를 NOT NULL FK로 참조하고 있었습니다.
  • 기존 deletePost()는 postRepository.delete(post)만 호출해, 부모를 먼저 지우려다 자식 행의 FK에 막혔습니다.

해결

삭제 순서를 "의존성 그래프의 리프부터"라는 원칙에 맞춰 서비스 계층에서 명시적으로 정리했습니다. (Notification → Comment·Reply·PostLike → Post)

@Transactional
public void deletePost(Long postId, Long userId) {
    Post post = ...; // 작성자 검증 생략

    // 1) 가장 바깥 리프: 댓글/대댓글에 걸린 알림
    List<Comment> topLevelComments = commentRepository.findByPostIdAndParentIsNull(postId);
    topLevelComments.forEach(notificationService::deleteNotificationsForComment);

    // 2) Post를 참조하는 자식들
    postLikeRepository.deleteByPostId(postId);
    commentRepository.deleteByPostId(postId); // 대댓글은 replies의 cascade REMOVE로 함께 정리

    // 3) 루트
    postRepository.delete(post);
}
  • 대댓글 → 원본 댓글 FK는 Comment.replies에 cascade = REMOVE, orphanRemoval = true를 두어 부모 댓글과 함께 지워지게 했습니다.
  • deleteNotificationsForComment()는 원본 댓글과 그 대댓글의 알림을 함께 지우며, 댓글 단건 삭제도 같은 메서드를 재사용합니다.

트레이드오프 — 왜 Post에 cascade를 걸지 않았나

방법장점한계
Post에 @OneToMany(cascade = REMOVE)코드가 짧음Notification은 Post와 양방향 관계가 없어 cascade로 지워지지 않음. 결국 수동 정리가 섞임
리포지토리 삭제 메서드로 명시적 정리 (채택)무엇이 함께 지워지는지, 삭제 순서가 코드에 드러남자식 엔티티가 늘면 서비스 코드도 함께 수정해야 함

Notification을 어차피 수동으로 지워야 한다면, Comment·PostLike도 같은 방식으로 일관되게 처리하는 편이 가독성과 유지보수에 유리하다고 판단했습니다.

결과

  • 댓글·대댓글·좋아요·알림이 모두 달린 게시물을 삭제하는 통합 테스트를 추가해 통과를 확인했습니다.
  • 게시물 삭제와 댓글 삭제가 같은 알림 정리 메서드를 쓰도록 통일되었습니다.

배운 점: 연관관계가 추가될 때마다 "이 엔티티를 지울 때 누가 나를 참조하는가"를 먼저 확인하는 습관이 생겼습니다.

4. [위드도그] 래퍼 타입 언박싱 NPE 및 예외 처리 기준 수립

위드도그 (WithDog) · with-dog

한 줄 요약: Nullable 래퍼 타입의 자동 언박싱으로 인해 발생하는 NPE 예외를 "값의 출처"와 "비즈니스 의미"에 따라 3단계 방어 체계로 정립했습니다.

문제

Double / Integer / Long 같은 래퍼 타입이 원시 타입 변수나 파라미터로 들어가는 순간 자동 언박싱이 일어나고, 값이 null이면 NPE가 발생합니다. 같은 원인의 NPE가 세 곳에서 나왔습니다.

사례발생 지점원인
1. 산책 응답WalkResponse.from()진행 중인 산책은 distanceKm이 null인데 record의 double 필드로 언박싱
2. 산책 코스 추천RecommendService.recommend()위치를 등록하지 않은 유저의 위도·경도를 double에 대입
3. 강아지 건강 상태 수정UpdateHealthConditionsRequest요청 바디에 값이 빠지면 null 리스트가 서비스까지 전달

사용자 입장에서는 세 경우 모두 원인을 알 수 없는 500 에러였습니다.

해결

사례 1 — null이 정상 상태인 도메인 값: 기본값
double distanceKm = walk.getDistanceKm() == null ? 0 : walk.getDistanceKm();
사례 2 — null이면 진행할 수 없는 도메인 값: 명확한 비즈니스 예외
if (user.getLatitude() == null || user.getLongitude() == null) {
    throw new BusinessException(ErrorCode.LOCATION_REQUIRED); // 400 + 안내 메시지
}
사례 3 — 신뢰할 수 없는 외부 입력: 시스템 경계에서 Bean Validation
public record UpdateHealthConditionsRequest(@NotNull List<String> healthConditions) {}

@PatchMapping("/{id}/health-conditions")
public ResponseEntity<Void> updateHealthConditions(@PathVariable Long id,
        @Valid @RequestBody UpdateHealthConditionsRequest request, ...) { ... }
값의 출처방어 수단이유
내부 도메인, null이 정상 상태null 체크 후 기본값"아직 측정되지 않음"은 오류가 아니므로 응답을 막을 이유가 없음
내부 도메인, null이면 진행 불가null 체크 후 비즈니스 예외사용자가 무엇을 해야 하는지(위치 등록) 알려줘야 함
외부 입력 (HTTP 바디)@Valid + @NotNull도메인 로직에 들어오기 전에 경계에서 원천 차단

결과

  • 세 API 모두 500 대신 의도한 응답(기본값 또는 400 + 안내 메시지)을 반환합니다.
  • RecommendServiceTest에 "위치 미등록 시 명확한 예외", "좌표를 직접 전달하면 등록 위치 없이도 추천 성공" 두 케이스를 추가했습니다.
  • 이후 같은 기준으로 회원가입·로그인 요청에도 입력 검증을 추가했습니다.

배운 점: 래퍼 타입이 원시 타입으로 흘러가는 지점은 모두 잠재적 NPE 지점으로 보고, 방어 수단은 값의 출처가 결정한다는 기준을 얻었습니다.

5. [moamoa] 하네스 기반 AI 에이전트 개발 파이프라인 구축

moamoa · 2026.09 · moamoa

한 줄 요약: 서울 전시·박람회·축제 검색 서비스 moamoa 개발 시, AI 에이전트를 단계별로 배치한 5단계 파이프라인을 설계하여 8일 만에 v0.1부터 v0.3까지 성공적으로 배포했습니다.
